# SQL subject: design

Date: 2026-11-24. Taral asked for the SQL subject next, ahead of Networks ("start the write code for SQL").
Claude recommended replaying the learner's own query clause by clause, and Taral said to start building;
that's taken as approval of that option. The Tintelix HLD and LLD (Claude Docs) already define most of the
subject; this note records what they decided and the calls made to build it.

## Intent

Teach SQL by doing: each lesson explains one statement, then the learner writes real queries against a
real Postgres running in the browser. After every run the stage replays what the query did, clause by
clause, on the learner's own rows: the rows WHERE dropped, the buckets GROUP BY made, the groups HAVING
removed. Mistakes are shown happening, not just reported. That replay is what sets Tintelix apart from
SQLBolt-style sites.

## Already decided (HLD and LLD)

- 21 lessons in 5 modules, PostgreSQL syntax: Reading rows (SELECT, WHERE, ORDER BY, DISTINCT,
  LIMIT/OFFSET), Summarising (COUNT/SUM/AVG, GROUP BY, HAVING, CASE WHEN), Combining tables (INNER JOIN,
  LEFT JOIN, WITH, ROW_NUMBER() OVER), Changing data (INSERT, UPDATE, DELETE), Defining tables (CREATE
  TABLE, ALTER TABLE, CREATE INDEX, DROP TABLE, TRUNCATE). The HLD's table gives each lesson's animation
  and what it builds on.
- Task lessons, not step-through diagrams: a short explanation, a syntax card, 3–5 tasks, a common-mistake
  note, Hint (always) and Show solution (after the first run). The stage replays the last run above the
  query editor; the run status sits under it; feedback, the result and a dataset card sit beside it.
- PGlite (Postgres compiled to WebAssembly, under 3 MB compressed) in a Web Worker, loaded only on SQL
  pages. A run longer than 3 s kills the worker, which is rebuilt.
- The checker reports the first problem: a Postgres error in plain words (42803 → "Every column in SELECT
  must be in GROUP BY or inside a summary like SUM"); column count or order (names only when the task
  names them); rows missing or extra, compared as multisets after normalising numbers, dates and NULLs, up
  to three of each shown; wrong order for an ordered task, with a "should be" rank per row. Change tasks
  run the learner's statement and the solution on fresh copies and compare a verify query.
- One made-up Tintelix Shop database (customers, orders, products) runs through every lesson. Prices in
  rupees.
- The build fails if a task's starter errors, its solution fails its own checker, an ordered task's answer
  has no ORDER BY, or an animation doesn't end on PGlite's real result.

## Goals of this build

- The SQL subject live at /sql with all 21 lessons listed, built one lesson per pull request like the
  case studies.
- First pull request: the engine (seed, runner, checker, stage builder), the task-lesson page, and lesson 1
  (SELECT) end to end. Later pull requests add one lesson each, extending the stage builder where a lesson
  needs it (CTEs, window functions, changes, table definitions).

## Non-goals (now)

Review cards and spaced review (Practice isn't built yet), accounts and sync, a general SQL playground,
replaying query shapes no lesson teaches (subqueries, set operations, several CTEs): those show their
result and feedback without a replay.

## Anti-goals

- A replay that disagrees with the real result. Every frame comes from running SQL in PGlite; the last
  frame must equal the real result or the replay is not shown.
- Feedback that only says "wrong". It must say what's wrong.
- SQL pages slowing the rest of the site. PGlite and the editor load only on SQL pages.

## Approaches considered (for the replay)

1. **Replay the learner's own query, clause by clause (chosen).** A SQL parser splits the query; each
   stage (FROM, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT) is rebuilt as SQL and run in
   PGlite to get the rows in between. Shapes it can't stage show the result only. Matches the HLD; the
   biggest engine piece.
2. **Animate only each lesson's own example**, precomputed at build time; learner runs show a result grid
   and feedback. About half the work, but the learner's own query never animates.

## Calls made (Claude's, open to change)

- **Shop schema.** customers (id, name, email, city nullable, country, signed_up), products (id, name,
  category, price, stock), orders (id, customer_id, ordered_at, status, total, coupon nullable), and an
  added **order_items** (order_id, product_id, quantity, unit_price) so products connect to orders. About
  20 customers (some with no orders, some with no city), 15 products in 4 categories, 60 orders and 150
  order lines, generated by one seed file with a fixed random seed; order totals equal their lines.
- **Isolation.** One PGlite per page. Every run is wrapped in BEGIN … ROLLBACK, so each run starts from the
  untouched seed (Postgres DDL is transactional too). Statements that control transactions themselves
  (BEGIN, COMMIT, ROLLBACK) are refused with a plain message.
- **Parser:** pgsql-ast-parser (pure JavaScript, parses and prints Postgres SQL). **Editor:** CodeMirror 6
  with SQL highlighting; Ctrl/Cmd + Enter runs.
- **Code layout:** a framework-free `packages/sql` (seed, plain-word errors, result comparison, checker,
  stage builder) that runs the same in Node tests and in the browser worker; React views in
  `apps/web/ui/sql`.
- **Lesson data:** a new `SqlLesson` schema beside the diagram `Lesson`: id, slug, topic, hook title,
  promise, minutes, explanation paragraphs, syntax card, common mistake, tasks (per the LLD's SqlTask:
  prompt, starter, hint, solution, answer, ordered, optional verify), builds-on and cheatsheet. Lesson ids
  are prefixed `sql-` (slugs are not), so progress keys never clash with System Design.
- **Page:** the existing lesson route renders a SQL lesson with its own view: lesson list on the left, then
  the explanation and tasks, and the replay, editor, run status, feedback and result. On phones the parts
  stack.
- **Progress:** solved task ids kept on the device (the store's preferences), and the lesson's progress set
  to tasks solved out of tasks, so the subject page and continue card work unchanged.
- **The subject card** counts SQL as live: the card shows a subject as open when it has written lessons,
  rather than by phase number.
- **Hook titles** written for all 21 lessons (for example GROUP BY: "Who spends the most?", from the HLD
  mock-up).

## Left to the builder

Exact replay timing and transitions; plain wording of error messages beyond the common Postgres codes;
the dataset card's layout; tasks and copy for each lesson within the HLD's description.
